# Backend Integration & Deployment Requirements for the Existing Application

## Objective

I have the existing backend repository and need to integrate my application/code into it without disrupting the current architecture or functionality.

The first step is to **thoroughly analyze the existing repository** to understand its architecture, authentication flow, database structure, API patterns, folder organization, and existing application logic. The integration should follow the conventions already established in the repository rather than introducing a separate or parallel implementation.

---

## 1. Existing Backend Analysis

Please review the complete backend repository and understand:

* Existing project and folder structure.
* Backend architecture and application flow.
* Existing APIs and their conventions.
* Authentication and login implementation.
* User/session management.
* Database models and data storage approach.
* Existing admin functionality.
* Access-control and authorization logic.
* How employee accounts are created and managed.
* How event-specific lead data is currently represented and stored.
* Existing frontend/backend integration points, if applicable.
* Existing configuration and environment-variable handling.
* Current deployment-related configuration.

The goal is to understand **how the existing system is designed before making any changes**.

---

## 2. Integrate My Application Into the Existing Backend

My existing application needs to be integrated into this backend as part of the existing system.

The integration should:

* Reuse the existing authentication/login mechanism.
* Follow the existing user and employee access-control structure.
* Use the existing database/storage approach wherever applicable.
* Follow the repository's existing API and coding patterns.
* Reuse existing utilities/components where possible.
* Avoid duplicating functionality that already exists.
* Avoid making unnecessary architectural changes.
* Keep the existing application functionality intact.

The final implementation should feel like a **native part of the existing backend**, rather than a separately developed application connected to it.

---

## 3. Admin-Based Employee Access

The existing application has an **admin functionality** through which access can be assigned to selected employees.

This access-control mechanism should remain intact and should also control access to the newly integrated functionality.

The expected flow is:

```text
Admin
  │
  ├── Selects/authorizes employees
  │
  ▼
Employee receives access
  │
  ▼
Employee logs into application
  │
  ▼
Authentication is validated
  │
  ▼
Authorization/access is checked
  │
  ▼
Employee can access the application
```

Employees who have not been granted access should not be able to access the exposed application functionality.

Do not create a separate authentication or authorization system if the repository already provides one.

---

## 4. Event-Based Lead Management

The application deals with **leads collected from different events**.

The existing repository already maintains information related to these events, so the integration should preserve this relationship.

The implementation should ensure that:

* Leads remain associated with the correct event.
* Existing event information is not lost or duplicated.
* Employee access follows the existing authorization rules.
* The newly integrated application uses the existing lead/event structure wherever possible.
* Data generated by the new functionality is stored in a way that remains consistent with the existing repository.

The complete flow should be understood before modifying the data models.

---

## 5. Data Storage

Please inspect how the existing backend currently stores application data and integrate the new functionality using the same approach.

Before creating any new tables, collections, models, or storage mechanisms:

1. Check whether an existing structure can be reused.
2. Reuse existing fields/models where appropriate.
3. Add new structures only when genuinely required.
4. Maintain relationships between employees, events, and leads.
5. Ensure existing data is not modified or corrupted.

The goal is to maintain **one consistent source of truth** within the backend.

---

## 6. Branch-Based Development

All integration work should be performed in a **new Git branch**.

Do not directly modify the existing/main branch.

The workflow should be:

```text
Existing Repository
        │
        ▼
Analyze Existing Code
        │
        ▼
Create New Feature/Integration Branch
        │
        ▼
Integrate Application
        │
        ▼
Run Tests
        │
        ▼
Validate Authentication & Access
        │
        ▼
Validate Data Storage
        │
        ▼
Commit Changes
        │
        ▼
Push Branch to Remote Repository
```

The branch should contain only the changes required for this integration.

---

## 7. Traffic and Performance Requirement

The application will be exposed through a URL by the **DevOps team**.

During the event, expected concurrent traffic may reach approximately **30 users**.

The implementation should therefore be checked for:

* Concurrent user handling.
* API response times.
* Database connection handling.
* File/data processing behavior.
* Session handling.
* Potential race conditions.
* Resource-intensive operations.
* Proper error handling.

The architecture does not need to be unnecessarily over-engineered for very large-scale traffic, but it should comfortably support the expected **~30 concurrent users**.

---

## 8. DevOps Integration

The DevOps team will handle exposing the application through the required URL.

Therefore, the development work should provide a backend that is deployment-ready and clearly communicates:

* Required environment variables.
* Required dependencies.
* Application startup command.
* Required ports/configuration.
* Database requirements.
* Any external service/API requirements.
* Authentication configuration.
* Any required storage configuration.

Do not make unnecessary infrastructure changes unless required for the application to function correctly.

---

## 9. Testing Requirements

Before considering the integration complete, test the following:

### Authentication

* Employee login works using the existing login mechanism.
* Invalid credentials are rejected.
* Sessions/tokens work correctly.
* Logout works as expected.

### Authorization

* Authorized employees can access the application.
* Unauthorized employees cannot access restricted functionality.
* Admin access continues to work.
* Existing permissions are not affected.

### Application Functionality

* The integrated application works correctly after login.
* Leads are associated with the correct events.
* Existing event-related functionality remains intact.
* New data is stored correctly.

### Concurrent Usage

Test the application with approximately **30 concurrent users** to identify:

* API bottlenecks.
* Database issues.
* Session problems.
* Unexpected failures.
* Performance degradation.

---

## 10. Minimize Unnecessary Changes

This is an important requirement.

**Do not rewrite or restructure the existing backend unnecessarily.**

Before modifying anything:

* Understand the existing implementation.
* Identify the smallest required integration points.
* Reuse existing components.
* Follow existing patterns.
* Preserve backward compatibility.
* Avoid introducing duplicate systems.

The objective is **integration, not redevelopment of the existing backend**.

---

## 11. Expected Final Outcome

The final repository should have:

```text
Existing Backend
       │
       ├── Existing Authentication
       ├── Existing Admin Access
       ├── Existing Employee Management
       ├── Existing Event/Lead Management
       │
       └── Newly Integrated Application
                │
                ├── Existing Login
                ├── Existing Authorization
                ├── Event-wise Lead Handling
                └── Existing Data Storage Pattern
```

The application should behave as a properly integrated feature of the existing backend.

The final changes should be committed and pushed to the **new feature/integration branch**, ready for review and subsequent deployment by the DevOps team.

---

## Primary Deliverable

The primary objective is:

> **Thoroughly analyze the existing backend repository, understand its authentication, authorization, event/lead management, and data-storage architecture, then integrate my application into that existing structure with minimal and necessary changes. The application must use the existing login and admin-controlled employee access system, correctly maintain event-wise lead data, support approximately 30 concurrent users, and be delivered through a new Git branch with all required code and configuration changes pushed to the repository.**
